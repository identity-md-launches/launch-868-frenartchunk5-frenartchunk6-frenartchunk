# IMD6900 Frens: the art, deployed by the IMD swarm

The on-chain art of the 2222 [IMD6900 Frens](https://imd6900.pages.dev) and the renderer that draws them, packed so the
IMD swarm can deploy them with IMD's `evm_contracts` launch: constructors only, static arguments, nothing called after.

- `src/FrenArtChunks.sol`: `FrenArtChunk1..7`, data contracts. Each one's code is a STOP byte (calling it does nothing)
  followed by up to 24,575 bytes of art: 69 layers (13 faces per character, 3 lab coats, 2 hats, 15 items,
  10 backgrounds) and a 256-colour palette, 141.6 KB in all.
- `src/FrenArtIndex.sol`: where every layer sits (chunk, offset, length), the colour tables, the face table, each
  chunk's code hash, and which chunks are framed.
- `src/FrenRenderer.sol`: draws a fren from its combo and seed: an 84x84 8-bit bitmap inside an SVG, with its traits,
  as `tokenURI(tokenId, combo, seed)` and `pendingURI(tokenId)`. Its constructor takes the seven chunks and every read checks
  their code hashes, so it can only ever draw this art. No owner, nothing to configure, nothing that changes.

IMD's launch admission reads every contract's code as instructions and refuses CALLCODE, DELEGATECALL and SELFDESTRUCT
bytes, even in code that can never run. Where a chunk's art happens to show one (chunks 4 and 7), the chunk is stored
framed: a PUSH32 byte before every 32 bytes of art, so the code reads as nothing but PUSH data. The renderer strips the
frames as it reads; `test_ChunksPassTheAdmissionScan` runs the same scan over every chunk, and
`test_RendererPassesTheAdmissionScan` checks the renderer. Both also enforce the runtime size limit.

Both Solidity files under `src/FrenArt*` are generated by `script/art/chunks.py` from `script/art/data` (the art kit's
export): never edit them by hand.

`FrenArtIndex.CHUNK_SIZES` is reference metadata. Despite its generated comment, the renderer does not read that
table: `_entry` checks the complete code hash on each read, which also rejects chunks of the wrong size.

## The frens and this art

The intended consumer is `IMD6900Frens`. The previously listed address,
`0x69004fEd3d8a34FFA952d15A128f74D8340fa79d`, returned empty code and nonce zero on Ethereum during the
2026-10-07 adaptation check. Its deployment, owner controls and renderer integration are unverified.
Before connecting the frens, confirm the actual deployed consumer supports `tokenURI(uint256,uint24,uint256)`
and `pendingURI(uint256)`. The local reference renderer verifies output compatibility, not a deployed consumer.

Metadata calls are expensive: the audit's samples use about 9–10.3M gas for `tokenURI` and 25.5M for
`pendingURI(1)`. A 25M `eth_call` allowance is insufficient for that pending sample. The explicit-budget test
checks both sample calls at 30M; this is not an upper bound for every input. Use an RPC allowance that also
covers the actual consumer's call overhead and test its metadata path before integration.

## Tests

`forge test` (offline, no RPC):
- `test_MatchesTheReference`: bitmaps identical to the art kit's reference renderer (`expected.json`);
- `test_SameAsTheLaunchRenderer`: byte for byte the same `tokenURI`, `pendingURI`, attributes and canvases as the
  vendored reference renderer (`test/ref/FrenRendererRef.sol`);
- `test_MetadataFitsThirtyMillionGas`: the audit's revealed and pending samples succeed within a 30M call budget
  and return the reference metadata;
- `test_DrawsOnlyThisArt`: with other chunks, or these in another order, every read reverts;
- `test_DeploysWithoutTheEarlierChunks`: a CREATE2 factory deploys launch 3 in order on a fresh chain, all seven
  renderer arguments are stored correctly, and reading missing art reverts `BadArt`;
- `test_ChunksPassTheAdmissionScan`, `test_RendererPassesTheAdmissionScan`: no application shows a refused opcode;
- `test/OnChainChunks.fork.t.sol` (MAINNET_RPC_URL): the chunks already deployed (launches #819 and #838) draw the reference.

`python3 script/check_launch_gas.py` builds with the existing configuration and starts a private, unforked Anvil
node (Prague with the transaction gas cap enabled). It sends all four launch-3 initcodes as calldata to the
test-only `LaunchGasFactory` in one CREATE2 transaction and checks the receipt against 95% of the 2^24 gas cap.
It also checks runtime sizes, admission opcodes and all constructor addresses. It needs Python 3 and the installed
Foundry tools, no packages, keys or external RPC. The old `test_LaunchesFitTransactions` was removed because
Forge's `gasleft()` deltas omitted code-deposit costs: it reported only 1.31M gas for launch 3. The deployed
launches #819 and #838 actually used 11,290,222 and 10,569,418 gas. The local launch-3 receipt used 14,179,144 gas
with Foundry 1.8.5 / solc 0.8.26, below the 15,938,355 check limit. The deployment service must still simulate
its actual factory overhead and policy ceiling; the local test factory does not implement that policy.

## The three launches (`evm_contracts`, Ethereum mainnet)

Ethereum caps a transaction at 2^24 gas and IMD deploys a launch in one, so the art goes in three. None of these
contracts has an owner; `owner` in the request is still the team wallet,
0x35da9c0303507ddf708e87f2568eddf12c47a059.

1. `FrenArtChunk1`, `FrenArtChunk2`: no constructor arguments.
2. `FrenArtChunk3`, `FrenArtChunk4`: no constructor arguments.
3. `FrenArtChunk5`, `FrenArtChunk6`, `FrenArtChunk7`, then `FrenRenderer` with seven address arguments, in order:
   the chunks from launches 1 and 2 (static addresses), then `$contract:FrenArtChunk5`, `$contract:FrenArtChunk6`,
   `$contract:FrenArtChunk7`.

Every read checks that its chunk is exactly this repository's, so a launch that changed the art can't produce a working
renderer. (Launch #854 was parked when the renderer still checked in its constructor: IMD's admission deploys a launch
on a fresh chain, where the earlier launches' chunks don't exist.)
